# 音视频输入输出蓝图（学自 Pr / Ae / Au）

> 2026-10-15。教材就是本机这三件：`E:\Pr`（Premiere Pro 2024，15129 文件）、`E:\Ae`（After Effects 2024，8795 文件）、
> `D:\Au`（Audition 2024，1184 文件）。做法是**读它们的部件结构**（只读，不动人家一个字节），
> 把架构上的规矩提炼成 KID 自己的设计，而不是搬代码。

---

## 1. 从它们的目录里读到的架构

三件共享同一套媒体核心，这是最要紧的一点：

| 部件 | 体积 | 它教会什么 |
|---|---|---|
| `mc_dec_avc.dll` / `mc_enc_avc.dll` | 7.61 / 8.87 MB | **解码与编码是两个独立模块**，各有各的名字与生命周期 |
| `CodecSupport.dll` | 3.6–3.9 MB | **「我能做什么」由一层登记表回答**，不是散落各处的 if |
| `ImporterXXX.prm`：MXF / F65 / RED / QuickTime / Lumetri / OpenEXR | 2–9 MB 每个 | **一种容器族一个导入器**：容器解析与编码解码分开 |
| `avcodec-59.dll` | 3.14 MB | 长尾格式**借力成熟实现**（FFmpeg 5 系），不自研每一个编解码器 |
| `MediaFoundation.dll`（Au） | 2.04 MB | 平台自带媒体栈作为**另一条后端** |
| `.epr` 导出预设（每件 8 个） | 小 | **导出参数是数据，不是代码** |
| 三件共用同一批模块 | — | **核心共享、外壳各异** |

## 2. 读成 KID 的六条设计

### 设计 1 · 解码器与编码器分家
每个格式族在 `deps/manifest.json` 里登记**两条**能力：`decode-<family>` 与 `encode-<family>`，
各自有独立的文件、哈希与状态。理由：能读不等于能写（FLAC 现在就是「读得到元数据、写还没做」）。

### 设计 2 · 「我能做什么」要有登记表
新增 `library_media op=capabilities`：**一处回答**「哪些容器能开、哪些编码能解、哪些能写」，
字段来自各解码器自报，而不是靠调用方猜。这与能力目录同源（自有词表 + 本地挂接）。

### 设计 3 · 容器与编码分层
**容器解析**（MP4 盒子 / Matroska EBML / RIFF / Ogg 页）与**编码解码**（PCM / Vorbis / Opus / FLAC）
是两层，互不知道对方的实现。`mkv` 里装 Opus 与 `ogg` 里装 Opus 只应是「容器适配」的差别。

### 设计 4 · 长尾借力，主流自研，且都要登记
重要且算法清晰的（PCM、FLAC）**自己写**；长尾（老编解码、专业 MXF 里的各种 essence）**借力**——
但借来的必须进 `deps/manifest.json`：来源、许可、哈希、用途一样不少。这正是那层依赖账本存在的理由。

### 设计 5 · 导出参数是数据
导出配置写成**数据文件**（对应 `.epr` 的位置），可以由界面生成、可以被保存、可以被 diff；
代码里只留「读配置 → 跑管线」。

### 设计 6 · 核心共享，外壳各异
KID 已经是这个形状了（引擎 + 桥 + 壳），音视频这一层照此办理：
解码在引擎里（可被任意宿主复用），播放与预览在壳里（`Windows.Media`），导出走 KPB 的端口。

## 3. 落地顺序（按「先立形状，再长肉」）

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | `library_media op=capabilities`：登记表 + 由解码器自报 | 一处能答「能开什么、能解什么、能写什么」 |
| 2 | 容器层补齐：Matroska（已能读时长/轨道）+ MP4 盒子 + RIFF/AVI + Ogg 页 | 对每族给出时长、轨道、编码 ID、分辨率/采样率 |
| 3 | 编码层：FLAC 编码（接上已有的 FLAC 读器，形成自家读写闭环） | 自编码 → 自解码 → 与源 PCM 逐字节一致 |
| 4 | 对外出口：`op=export`（WAV/FLAC 先落地，MP3 与视频后议） | 导出文件被独立工具认作合法 |
| 5 | 借力长尾：把「外部解码器」作为**登记过的依赖**接入 | 依赖账本里看得见，缺了会明确报「未安装」而不是静默失败 |

## 4. 与既有纪律的衔接

- **律 2（探测有界）**：读容器只读头部若干字节，`limit` 可配；
- **律 3（判不了就说判不了）**：能读的就说能读，不能的明确拒绝（视频首帧解码目前**不做**）；
- **律 8（同一件事只实现一次）**：容器解析只在一个地方，导入器不许各自解析一遍；
- **律 10（依赖可见）**：借力 FFmpeg 一类实现必须登记、写清许可与哈希。
